# 1.0 사용자 경험 자동 검수 — 첫 기준선

작성일: 2026-09-12  
기준 문서: `UX-AUTOMATED-REVIEW-v0.1.md`  
기준 viewport: **375 × 812 CSS px** — iPhone 13 mini 세로 화면을 대표하는 자동 브라우저 기준

이 문서는 자동 UX 검수 체계를 실제 CI에 연결한 첫 실행 결과를 기록한다. 기능 단위 테스트와 별도로, 전술 화면의 정보 배분과 콘텐츠 간 이동 흐름을 회귀 기준으로 삼기 위한 기준선이다.

---

## 1. 현재 자동화 구성

### CI 실패로 막는 UX 계약

`tests/ux-contract.test.cjs`

- 전술 화면의 기본 순서가 `목표 → 판 → 상태 메시지 → 단어 → 조작`을 유지한다.
- safe-area와 `viewport-fit=cover`를 유지한다.
- 기본 전술 칸과 단어 버튼은 최소 44px 터치 크기를 유지한다.
- 완료 화면에서 `다시 해보기`는 secondary, 다음 본편 진행은 primary다.
- stage 완료 뒤 다음 story/stage 노드가 있으면 여정 목록을 불필요하게 경유하지 않는다.
- story 마지막 버튼은 다음 노드에 맞춰 `스테이지 시작 / 이야기 계속 / 월드맵으로`를 예고한다.
- replay 종료는 본편 진행과 분리한다.

### 경고로 남기는 정적 휴리스틱

`tools/ux-audit.cjs`

현재 첫 기준선에서 다음 세 경고가 발생한다.

1. `UX-05` — 마지막 행동 뒤 **120ms** 만에 완료 시트가 열린다.
2. `UX-01/02` — 목표 글자는 **18px**, 상태 메시지는 **14px**다.
3. `UX-01/02` — 목표는 독립 카드+그림자를 사용하지만 상태 메시지는 가벼운 반투명 면이다.

이 세 항목은 코드만으로 실패 판정하지 않는다. 실제 모바일 스크린샷과 함께 판단한다.

### 실제 브라우저 검수

`tests/smoke_ux.py`

GitHub Actions에서 Python Playwright + Chromium을 사용해 375×812 모바일 viewport를 실제 렌더한다.

대표 화면:

- 길목 G1 첫 진입
- 길목 G1 일반 행동 후 상태 메시지
- 장인골 W2 첫 진입
- 장터 M8 첫 진입
- 스테이지 완료 시트
- story → stage 직접 전환

검수마다 스크린샷을 `ux-screenshots` Actions artifact로 7일간 보존한다.

## 2. 첫 실행 결과

최종 CI 실행: `af841066f0ba6f76782257f62a96bdaa6dbbb5b9`  
결과: **성공**

기존 Node 테스트와 새 UX 계약 테스트, 정적 UX 감사, 모바일 브라우저 스모크가 모두 실행된다.

### 길목 G1

| 영역 | y / 높이 |
|---|---:|
| 목표 | `62 / 67.3px` |
| 판 영역 | `137.3 / 512.7px` |
| 실제 격자 | `196.6 / 394px` |
| 상태 메시지 | `658 / 34px` |
| 단어 | `700 / 44px` |
| 조작 | `752 / 48px` |
| 문서 전체 | `812px` |

**판정:** 한 화면 안에 목표·판·상태·단어·조작이 모두 들어간다. 가로 넘침도 없다.

다만 첫 화면에서 목표 카드는 그림자와 굵은 18px 글자로 강하게 보이고, 행동 전의 중립 상태 메시지는 화면 하단의 가벼운 영역으로 보인다. 이것이 플레이 중 정보 위계로 적절한지는 이후 조정 후보로 남긴다.

### 장인골 W2

| 영역 | y / 높이 |
|---|---:|
| 목표 | `62 / 67.3px` |
| 판 영역 | `137.3 / 496.9px` |
| 장치 판 | `178.9 / 413.7px` |
| 상태 메시지 | `642.2 / 49.8px` |
| 단어 | `700 / 44px` |
| 조작 | `752 / 48px` |
| 문서 전체 | `812px` |

**판정:** 장치 판이 풍부해도 한 화면 안에 모든 필수 조작이 들어간다. 상태 메시지는 G1보다 두 줄로 커지지만 아직 viewport 안에 유지된다.

### 장터 M8

| 영역 | y / 높이 |
|---|---:|
| 목표 | `62 / 127.6px` |
| 판 영역 | `197.6 / 437.8px` |
| 장터 판+상황 패널 | `200.6 / 431.8px` |
| 상태 메시지 | `643.3 / 68.7px` |
| 단어 | `720.0 / 44px` |
| 조작 | `772.0 / 48px` |
| 문서 전체 | `832px` |

**발견:** 812px viewport보다 문서가 **20px 길다.** 하단 조작의 끝은 약 `820px`에 있다.

첫 브라우저 검수에서는 이를 P0 실패가 아니라 **P1 화면 배분 경고**로 분류한다.

이유:

- 가로 넘침은 없다.
- 모든 터치 대상은 최소 44px를 유지한다.
- 스크롤하면 조작 가능하다.
- 넘침이 20px로 작아 진행을 막지는 않는다.
- 그러나 `목표 + 규칙` 카드가 127.6px로 G1/W2의 약 두 배가 되었고, 상태 메시지도 68.7px로 커져 플레이 현장과 하단 조작을 밀어내고 있다.

따라서 M8은 **목표 안내를 더 간결하게 만들거나, 목표/규칙의 시각 무게와 공간을 줄이는 설계 검토의 대표 사례**로 삼는다.

자동 검수에서는 96px를 넘는 세로 초과, 가로 초과, 44px 미만 터치 대상을 하드 실패로 잡고, 그보다 작은 세로 스크롤은 수치와 스크린샷을 경고로 남긴다.

## 3. 이동 흐름 기준선

현재 구조 검수는 다음 항목을 통과했다.

- story 마지막에서 다음이 stage라면 버튼이 `스테이지 시작`으로 표시된다.
- 버튼을 누르면 여정 목록을 거치지 않고 바로 전술 화면으로 들어간다.
- stage 완료 뒤 다음 node가 있으면 `continueFromNode → playNode`로 직접 이어진다.
- 완료 화면의 `다시 해보기`는 secondary, `이야기 계속 / 다음 스테이지 / 월드맵으로`가 primary다.

따라서 **불필요한 월드맵·여정 왕복은 현재 상위 흐름 구조에서는 발견되지 않았다.**

다음 검수에서 더 볼 것은 화면 경로 자체보다 다음 두 가지다.

1. 완료 시트의 `stage.story`와 바로 뒤 after-story가 같은 사실을 반복하는가.
2. 마지막 판 변화 → 성공 메시지 → 완료 시트가 120ms 안에 넘어가면서 결과를 볼 시간을 빼앗는가.

## 4. 첫 기준선에서의 우선 수정 후보

### P1-A — 목표와 상태 메시지의 화면 배분

대표 질문:

> 플레이 시작 전에는 목표가 중요하지만, 행동을 시작한 뒤에도 목표 카드가 계속 가장 강한 정보여야 하는가?

현재는 목표가 더 큰 글자와 독립 카드·그림자를 사용한다. 상태 메시지는 판 아래에 붙어 있으나 시각적으로 더 조용하다.

수정 전에는 다음 비교를 먼저 한다.

- 목표 카드의 패딩·글자 크기·그림자를 줄인 안
- `goal`과 `ruleline`을 한 덩어리로 두지 않고 보조 규칙을 더 조용하게 만든 안
- 상태 메시지가 `good / bad / info`일 때만 시각적 존재감을 높이는 안

목표는 상태 메시지와 경쟁시키는 것이 아니라 다음 역할을 분명하게 하는 것이다.

- 목표 = 이번 판의 의도
- 판 = 현재 상태
- 상태 메시지 = 방금 한 행동의 의미

### P1-B — 마지막 결과를 볼 시간

현재 기본 전술 런타임은 승리 판정 뒤 약 120ms 후 완료 시트를 연다.

다음 자동 검수 확장에서는 마지막 행동 직후와 완료 시트 등장 시점을 브라우저에서 직접 기록한다. 이때 단순히 지연 시간을 늘리기보다, 마지막 세계 변화가 실제로 인지 가능한지를 기준으로 한다.

### P1-C — 완료 문장과 후일담 중복

현재 이동 경로 자체는 자연스럽다. 다음 단계에서는 `stage.story → after-story 첫 beat`를 인접 쌍으로 추출해 중복 후보를 자동 보고한다.

자동 문장 유사도는 실패 판정으로 쓰지 않는다. 같은 사건을 요약하고 인물의 반응으로 이어가는 의도적 반복도 있기 때문이다.

## 5. 운영 원칙

- UX 계약 위반은 CI를 실패시킨다.
- 시각적 위계와 작은 세로 초과는 우선 경고와 스크린샷으로 남긴다.
- 자동검사의 현재 구현을 디자인의 정답으로 고정하지 않는다.
- 화면 설계를 바꾸기로 결정했다면 테스트도 새 원칙에 맞춰 함께 수정한다.
- iPhone 13 mini Safari 실기기 검수는 자동 Chromium 검수를 대체하지 않고 최종 확인으로 유지한다.

첫 기준선의 목적은 “현재 화면을 그대로 보존”하는 것이 아니라, **변경 전 상태를 수치·흐름·스크린샷으로 남겨 이후 개선이 실제로 나아졌는지 비교할 수 있게 하는 것**이다.
