# 재사용 가능한 게임 규칙·기믹 도감 v0.1

작성일: 2026-09-10

이 문서는 튜토리얼 6판과 길목 G1까지 실제로 구현·검증한 규칙을, 이후 스테이지에서 다시 조합해 쓸 수 있도록 정리한다.

> **2026-10-27 추가:** 학술탑 03B의 이야기-연구 전환, 출처와 작성 주체 분리, 맥락별 의미 작업, 다섯 빈칸 직접 드롭다운을 **13장에 재사용 상태별로 정리**했다. 기존 1~12장의 전술 기믹 기록은 당시 이력으로 보존한다.

목적은 스테이지마다 전용 코드를 계속 늘리는 것이 아니라, **이미 검증한 작은 규칙을 조합해 새로운 단어 경험을 만드는 것**이다.

이 문서는 아이디어 목록이 아니다. 실제 구현 상태를 다음 세 단계로 구분한다.

- `✅ 재사용 가능`: 현재 구조에서 그대로 또는 데이터 변경만으로 다시 쓸 수 있다.
- `🟨 일반화 필요`: 동작 자체는 검증됐지만 특정 스테이지·타일 이름에 코드가 묶여 있다.
- `⬜ 예정`: 아직 구현하지 않은 다음 공통 기믹이다.

---

## 1. 공통 설계 모델

현재까지의 좋은 기믹은 대부분 다음 구조로 설명할 수 있다.

> **행동/사건 → 조건 판정 → 상태 변화 → 피드백**

그리고 스테이지 완료는 여러 상태 조건의 조합이다.

예를 들어 G1 `관문 안의 길표지`는 다음과 같다.

1. `D → I` 이동
2. 경계 바깥에서 안쪽으로 이동했는지 판정
3. `entered = true`
4. `已進入關口。` 피드백
5. 길표지 조사 후 `inspected = true`
6. 다시 `D → 바깥` 이동
7. `exited = true`
8. `entered && inspected && exited`이면 완료

즉 새 중국어 단어를 구현할 때 가장 먼저 정해야 하는 것은 전용 버튼이나 효과가 아니라, **그 단어가 판 위의 어떤 관계·상태 변화로 보일 것인가**다.

## 2. 전술 핵심 규칙

| 규칙/기믹 | 상태 | 현재 사례 | 재사용 방법 |
|---|---|---|---|
| 상하좌우 한 칸 이동 | ✅ | 모든 전술판 | 기본 이동 규칙으로 유지한다. |
| 이동 불가 지형 | ✅ | 수풀, 석비, 길표지 | 타일을 통과할 수 없게 하여 경로 선택을 만든다. |
| 목적지 도착 | ✅ | `到達`, 출구 | 특정 타일에 도달했는지를 완료 조건으로 쓴다. |
| 인접 거리 판정 | ✅ | `接近`, 길표지 조사 | 상하좌우 한 칸 관계를 조건으로 쓴다. |
| 위험 칸 진입 거부 | ✅ | `避開`의 가시 | 잘못된 행동을 확정하지 않고 정보만 준다. |
| 이동하는 위험 대상 | ✅ | 늑대 | 고정된 순환 경로와 위험 반경을 데이터로 지정한다. |
| 한 턴 기다리기 | ✅ | 튜토리얼 Stage 5 | 플레이어 위치는 유지하고 움직이는 대상의 상태만 진행한다. |
| 되돌리기 | ✅ | 모든 전술판 | 직전 행동 전 상태를 복원한다. |
| 여러 조건을 모두 만족해 완료 | 🟨 | `stone + at_exit`, `crossed + at_exit`, G1 3조건 | 현재 조건 이름이 코드에 등록돼 있다. 종류가 늘어나면 일반 predicate registry로 바꾼다. |

### 2.1 이동은 단어 효과가 아니다

`接近`을 눌러 순간이동하거나 `避開` 버튼을 눌러 위험을 제거하지 않는다.

플레이어가 평범한 이동을 이용해 직접

- 가까워지고,
- 멀어지고,
- 통과하고,
- 도착하고,
- 피하는

상태를 만든다.

이 원칙은 이후 단어에도 유지한다.

## 3. 거리와 위험

### 3.1 인접 판정 `dist === 1`

상태: `✅`

현재 상하좌우 한 칸 거리는 여러 곳에서 공통으로 사용한다.

- 석비에 `接近`
- 길표지 조사 가능 여부
- 늑대의 위험 범위

대각선은 한 칸으로 취급하지 않는다.

현재 거리 계산은 맨해튼 거리다.

이 규칙은 다음 G2 `距離 / 範圍`의 기반이 된다.

### 3.2 위험 범위

상태: `✅`

늑대는 `cycle + radius`로 움직임과 위험 범위를 가진다.

행동을 확정하기 전에 현재 위치와 다음 위치의 위험 범위를 함께 검사한다. 위험하면 해당 행동을 취소하고 위치·턴을 소비하지 않는다.

이 패턴은 늑대가 아닌 다른 대상에도 재사용 가능하다.

예:

- 감시병 시야
- 불꽃이 번지는 범위
- 종소리나 신호가 닿는 범위
- 움직이는 수레의 충돌 예상 영역

다만 코드와 데이터 명칭이 현재 `wolf`에 묶여 있으므로 두 번째 이동 위험 대상이 등장하면 일반화한다.

### 3.3 기다리기

상태: `🟨`

플레이어가 움직이지 않고 외부 대상의 상태만 한 단계 진행시킨다.

전술적으로는 이미 매우 유용하다. 다만 현재 UI 노출 조건이 `wolf` 존재 여부에 묶여 있다.

두 번째 시간 진행형 기믹이 등장하면 `hasTurnCycle` 같은 일반 조건으로 바꾼다.

## 4. 접근·통과·진입·퇴출

이 네 가지는 비슷해 보이지만 판정이 다르다. 이후 공간 단어 설계에서 중요한 기준이다.

### 4.1 접근 `接近`

상태: `🟨`

현재 구현:

- 특정 대상과 상하좌우 한 칸 거리가 되면 상태가 바뀐다.
- 튜토리얼에서는 석비가 반응하고 문이 열린다.

재사용 가능한 개념은 **proximity trigger**다.

현재 상태 이름과 대상이 `stone / K`에 묶여 있으므로 다른 인접 반응 대상이 하나 더 생기면 일반화한다.

후보 형태:

`proximityTriggers: [{ target:'...', distance:1, flag:'...' }]`

### 4.2 통과 `通過`

상태: `🟨`

현재 구현:

- 통로 한쪽 입구로 들어간다.
- 통로 영역을 지난다.
- 다른 쪽 입구로 빠져나와야 `crossed = true`가 된다.

중요한 의미는 단순히 어떤 타일을 밟는 것이 아니라 **A 쪽에서 들어가 B 쪽으로 나가는 경로 관계**다.

현재 구현 이름이 `ruin / portals / crossed`에 묶여 있다. 다리, 문, 골목 등 두 번째 통과 기믹이 생기면 `passage` 개념으로 일반화한다.

### 4.3 진입 `進入`

상태: `✅`

현재 G1에서는 경계 타일 `D`를 기준으로 바깥에서 안쪽 타일 `I`로 이동하면 성립한다.

핵심은 특정 위치가 아니라 **경계 밖 → 경계 안**의 상태 전이다.

같은 구조로 다음을 표현할 수 있다.

- 건물 안으로 들어가기
- 작업 구역에 진입하기
- 감시 범위에 들어가기
- 특정 지역 안으로 물체를 옮기기

### 4.4 퇴출 `退出`

상태: `✅`

안쪽에서 경계를 지나 바깥으로 나오면 성립한다.

`通過`와 달리 반대편 출구가 필요하지 않다. 들어왔던 문으로 다시 나와도 된다.

G1에서는 길표지 확인이라는 선행 조건을 붙여, 단순 왕복이 아니라 `進入 → 볼일 → 退出`의 생활 상황을 만들었다.

## 5. 살펴보기와 상호작용

### 5.1 직접 살펴보기

상태: `✅`

별도의 `살펴보기 ↔ 이동으로` 모드는 사용하지 않는다. 정보가 유용한 대상은 평상시에 직접 누르고, 진행에 필요한 근접 조사는 상황형 행동 버튼으로 실행한다.

현재 사례:

- 늑대를 직접 눌러 다음 행동과 위험 범위 확인
- 시장의 좌판·사람·짐을 직접 눌러 정보 확인
- 장인골 W6의 톱니를 직접 눌러 손상 여부 확인
- 길표지·문·장애물·버섯 가까이에서 상황형 조사 행동 실행

통행 가능한 인접 칸은 탭하면 이동하는 원칙을 우선한다. 원거리 정보 확인과 실제 자원 이동·거래 행동은 구분하며, 시장의 실제 행동은 대상과 인접할 때만 가능하다. 바닥·벽처럼 별도 정보가 없는 칸에는 조사 화면을 열지 않는다.

살펴보기는 공략을 주는 것이 아니라 **판의 규칙과 현재 대상을 확인하는 정보 행동**으로 사용한다.

### 5.2 인접한 문맥 행동

상태: `✅`

G1 실기기 검수에서 나온 공통 UX 규칙이다.

플레이어 바로 옆에 명확한 상호작용 대상이 하나뿐이면,

`살펴보기` → `길표지 살펴보기`

처럼 버튼 이름을 상황에 맞게 바꾸고 한 번의 탭으로 실행한다.

대상도 조사 가능 상태로 표시한다.

인접 행동 대상이 없으면 하단 조사 버튼을 숨긴다. 같은 우선순위의 대상이 여러 개면 대상 칸들을 강조하고, 플레이어가 원하는 칸을 직접 눌러 선택한다.

현재 `interaction-runtime.js`는 각 스테이지의 `contextActions`를 읽어 대상·조건·우선순위·버튼 라벨·실행 동작을 공통으로 판정한다.

권장 형태:

`상호작용 대상 → 조건 → 버튼 라벨 → 실행 동작`

예:

- 상자 + 인접 → `상자 열기`
- 장치 + 인접 → `수문 조절하기`
- NPC + 인접 → `길지기에게 말 걸기`

## 6. 실패와 피드백 규칙

### 6.1 실패 비용은 낮게

상태: `✅`

초기 스테이지에서 잘못 판단했다고 즉시 게임 오버시키지 않는다.

현재 사례:

- 유적을 통과하지 않고 출구에 도착 → `還沒通過遺跡。`
- 위험 칸을 밟으려 함 → 행동 취소 + 위험 메시지
- 늑대에게 너무 가까운 이동 시도 → 행동 취소 + 위험 메시지
- G1에서 표지를 안 보고 퇴출 → 퇴출 자체는 허용하지만 완료되지 않음 + `路標還沒看。`

잘못된 선택은 처벌보다 **다음 판단에 쓸 정보**를 남겨야 한다.

### 6.2 위험 행동은 가능하면 확정 전에 막는다

상태: `✅`

위험 칸·늑대 범위처럼 명확히 위험한 행동은 현재 위치를 망가뜨리지 않는다.

이 방식은 특히 모바일 학습게임에서 실수 탭과 전략 실패를 구별하는 데 유리하다.

### 6.3 상태 변화는 즉시 보인다

상태: `✅`

상태 변화에는 최소 하나의 피드백을 준다.

- 목표 단어 완료 표시
- 타일 상태 변화
- 짧은 중국어 + 한국어 상태 메시지
- 필요한 경우 캐릭터 표정 반응

같은 정보를 여러 UI에 과도하게 반복하지 않는다.

## 7. 목표 조건 조합

현재 `win` 배열은 여러 조건을 AND로 묶는다.

현재 조건:

- `at_exit`
- `stone`
- `crossed`
- `entered`
- `inspected`
- `exited`

예:

- Stage 1: `stone + at_exit`
- Stage 3: `crossed + at_exit`
- G1: `entered + inspected + exited`

이 구조 덕분에 하나의 단어를 버튼 효과로 만드는 대신 **여러 작은 상태를 조합한 과제**를 만들 수 있다.

상태: `🟨`

현재 `isWin()`과 목표 강조가 조건 이름을 직접 알고 있다. 조건 종류가 계속 늘어나기 전에 다음 구조로 일반화하는 것이 좋다.

- `predicate registry`: 조건 ID → 판정 함수
- 목표 문구와 predicate 연결
- 스테이지별 전용 boolean을 줄이고 공통 flag/state 사용

단, G2 하나를 만들기 위해 미리 거대한 규칙 엔진을 만들지는 않는다.

## 8. 이야기·여정에서 재사용 가능한 진행 규칙

전술 기믹뿐 아니라 콘텐츠 흐름에도 재사용 가능한 규칙이 생겼다.

| 규칙 | 상태 | 설명 |
|---|---|---|
| `story → stage → story` 직접 연결 | ✅ | 정상 진행에서는 메뉴를 거치지 않는다. |
| `requires` 기반 노드 해금 | ✅ | 저장된 결과에서 열린 노드를 계산한다. |
| 지역별 병렬 section | ✅ | 길목·장인골·장터는 서로 자동으로 이어지지 않는다. |
| 다시 보기/다시 플레이 분리 | ✅ | replay는 본편 진행과 체크포인트를 바꾸지 않는다. |
| 중단 후 이어하기 | ✅ | 마지막 story beat 또는 tactical node를 저장한다. |
| 여정 전체 초기화 | ✅ | 1.0 이전 반복 플레이테스트를 위한 개발 편의 기능이다. |
| milestone으로 역할 계산 | ✅ | `소년/용사`를 문자열로 저장하지 않고 완료 조건에서 계산한다. |

이 규칙은 새 지역을 추가할 때 그대로 반복한다.

## 9. 현재 코드에서 일반화가 필요한 부분

새 기능을 만들 때 아래 항목은 무조건 즉시 리팩터링하지 않는다. **두 번째 실제 사용처가 생길 때 일반화한다.**

### 우선순위 A — 두 번째 사용처가 생기면 바로 일반화

1. `interaction-runtime.js`의 `L` 길표지 전용 `actionFor()`
2. `stone / K`에 묶인 인접 반응
3. `ruin / crossed`에 묶인 통과 판정
4. `wolf`에 묶인 이동 대상·기다리기

### 우선순위 B — 조건 종류가 더 늘면 일반화

1. `isWin()`의 조건별 하드코딩
2. `renderGoal()`의 단어별 하드코딩
3. `state.stone / crossed / entered / inspected / exited` 같은 개별 플래그

목표는 추상화 자체가 아니다.

> **같은 의미의 규칙을 두 번 구현하려는 순간 공통 규칙으로 올린다.**

## 10. 다음으로 추가할 공통 기믹

### G2 `距離 / 範圍`

상태: `⬜ 예정`

G2에서 새로 만들어야 할 공통 규칙 후보는 다음과 같다.

- 두 대상 사이 거리 읽기
- `거리 <= n`, `거리 > n`, `거리 == n` 판정
- 특정 중심에서 일정 거리까지의 범위 계산
- 판 위에 범위를 보조 표시하되 정답 경로는 표시하지 않기
- 하나의 범위 안/밖에 여러 대상이 있는지 판정

이미 있는 맨해튼 거리 함수를 기반으로 만들 수 있다.

이 기믹은 이후에도 재사용 폭이 매우 크다.

예:

- 경비 시야
- 종소리
- 화살 사거리
- 폭발/회복 범위
- NPC와 유지해야 할 거리
- 짐수레 사이 간격

따라서 G2는 `종소리 전용 코드`보다 **distance / range라는 공통 관계**를 구현하는 것을 우선한다.

### 이후 예정

- `路線 / 經由`: 경로 기록과 필수 경유지
- `位置 / 周圍 / 障礙`: 위치·주변 관계와 조사 결과
- `移動 / 前進 / 後退`: 플레이어 외 대상 이동
- `跟隨 / 帶領`: 두 유닛 사이의 주체·종속 이동
- `改變 / 保持`: 상태값 변경과 유지
- `增加 / 減少 / 調整`: 수치 변화
- `集中 / 分配`: 제한 자원의 이동과 배분

아직 구현 전이므로 이 문서에서는 규칙을 확정하지 않는다.

### 13.3 의미별 작업 유형 — 단어 뜻이 조작을 결정한다

같은 전역 스테이지 안에서도 모든 과제를 오지선다·같은 빈칸으로 만들 필요는 없다. **입력 형태를 단어와 자료가 요구하는 사고에 맞춘다.**

| 03B에서 실제 쓴 형태 | 플레이어가 구별하는 것 | 화면상의 행동 | 일반화 후보 |
|---|---|---|---|
| `仍然` — 옛 지도/현재의 목격 비교 | **지속된 사실**과 확인되지 않은 추측 | 둘의 자료를 읽고 남길 중국어 관찰 하나를 선택 | 서로 다른 시점·화자의 관찰로 지속/변화를 구별 |
| `當然` — 지도 표시/익명 쪽지 대조 | **자료에서 보이는 것**과 필자의 확신 | 쪽지에서 작성자의 판단 부분에 검토 표시 | 인용·주장·증거 출처 표시 |
| `固然` — 앞부분 인정 + 현재 경험 | 기록상 사실은 남기되 **다른 시점의 정보**도 덧붙이기 | 연구원이 이미 쓴 앞문장을 먼저 보여 주고 이어 쓸 문장 선택 | 주어진 앞부분을 고정하고 의미상 뒷부분만 고르기 |
| `不盡然` — 봉투 의견 검토 | 사실 자체와 **과하게 넓힌 판단 범위** | 원본은 건드리지 않고 검토용 문장에서 고칠 표현만 선택·수정 | 사실 보존·추론 제한·보고서 교정 |
| `突然` — 일상 사건 | **예고 없이 발생**한 사건 자체 | 인물이 겪는 짧은 이야기에서 사용, 정오답 없음 | 설명보다 장면이 의미를 전달하는 경우 읽기 전용 |
| T6 — 함께 남긴 기록 | 앞서 배운 표현들이 **서로 다른 문맥에서 어떻게 기능하는지** | 각 문장 안의 빈칸에서 표현을 선택해 하나의 연구 기록 완성 | 필요한 경우에만 종합 복원. 숫자 5는 고정 규칙 아님 |

**오답은 틀린 판단의 종류를 겨냥한다.** ‘쉼터 하나만 봤다’ → ‘두 곳 모두 남았다’처럼 관찰 범위를 넘겼는가, 쪽지 작성자의 주장만으로 마을 전체를 확정했는가, 과거와 현재 시점을 뒤섞었는가 등을 말한다. 정답 글자나 선택지 위치를 외워도 **왜 그 자리를 골라야 하는지**를 다시 생각하게 만들어야 한다.

### 13.4 원본·작성 주체·플레이어 행동을 따로 설계한다

여러 사람이 공동 작업하는 연구에서는 **‘내가 누르는 버튼’과 ‘소년이 쓴 문장’과 ‘연구원이 쓴 문장’이 동의어가 아니다.**

| 표시 요소 | 체크할 질문 | 실제 03B 사례 |
|---|---|---|
| `sourceLabel` / 원본 출처 | 어떤 시대·누구의 자료인가? 실제 보았는가, 전해 들었는가? | 옛 지도 / 소년이 본 현재 길 / 작성자 미상의 봉투 평가 |
| `workLabel` / 작업면 주체 | 누가 쓴 원고를 지금 만지는가? | 소년의 비교 메모 / 연구원의 해설 초안 / 봉투 평가의 검토문 / 두 사람의 공동 연구 기록 |
| `workContext` / 필요할 때만 짧게 | 왜 그 문장을 고치거나 덧붙이는가? | 연구원이 익명 주장을 검토하려고 **옮겨 적은** 문장은 두 사람의 잘못된 결론이 아니다 |
| `question` / 현재 행동 | 플레이어는 직접 무엇을 판단하나? | “소년이 목격한 무엇이 계속되나?”, “연구원 문장에 무슨 정보를 더하나?” |
| `confirmLabel` / 확인 동작 | 무엇을 확정하면 어떤 결과가 남나? | 주장 표시 / 문장 이어 쓰기 / 과장된 평가 고치기 / 기록 검토 |

이 필드들을 **모든 과제에 기계적으로 다 채우지는 않는다.** 원본과 작업면 제목만으로 충분하면 설명 한 줄을 더 만들지 않는다. 꼭 필요한 초안의 앞문장은 선택 **전부터** 표시하고, 선택 뒤 완성문은 중복으로 여러 번 쌓지 않는다.

### 13.5 종합 과제의 재사용 조건 — T6의 다섯 빈칸에서 추출

다음 조건이 맞을 때 **맥락형 빈칸 복원**을 후보로 삼을 수 있다.

1. 앞선 단계에서 같은 표현 묶음의 역할을 이미 *서로 다른 경험*으로 만났다.
2. 다시 푸는 이유가 명확하다. 예: “오늘 공동으로 남길 연구 기록을 완성한다.”
3. 표현마다 그 자리에 와야 하는 **문장 내부 의미 근거**가 있다. 앞문제의 정답 문장을 복사해 넣는 것이 아니다.
4. 현실 세계의 자료를 다룬다면 **사건 서술 / 타인의 인용문 / 최종 판단**을 구역·인용부호로 구분한다. 목표어가 모두 하나의 화자의 의견이 될 필요는 없다.
5. 종합해야 할 표현 수만큼 빈칸을 만들며, **‘다섯 개’ 자체는 재사용 규칙이 아니다.** 의미상 필요 없다면 종합 빈칸을 생략한다.

**현재 03B에서 검증한 입력·피드백 계약**

- 빈칸 자체가 ≥44px 버튼이다. 누르면 **그 문장 바로 아래** 하나의 드롭다운이 열리고 표현을 선택하면 닫힌다. 화면 아래 동일한 단어 목록을 다시 놓지 않는다.
- 배치된 표현도 목록에 나타나며 다른 칸에서 골랐을 때 **이동하거나 서로 교환**한다. 정밀 드래그는 필수가 아니다.
- 같은 표현을 두 칸에 중복 배치하지 않는다. 모든 칸을 채워야 ‘기록 검토’를 누를 수 있다. **선택했을 때와 정답을 검토할 때는 별도 동작**이다.
- 틀린 배치는 지우지 않으며 검토 후 **맞는 칸만 설명, 틀린 칸은 재독 요청**을 표시한다. 메뉴를 여는 것만으로 이전 판정이 지워지지는 않고, 실제로 배치를 바꿨을 때 재검토 상태로 전환한다.
- 한 번 더 탭·‘닫기’·바깥 탭·Esc로 닫는다. 작은 화면에서는 목록이 정상적인 문서 흐름에서 펼쳐져 부모 스크롤에 가리지 않아야 한다.
- 현재 `placements`, 선택 빈칸 `slot`, `clozeMenuOpen`, 선택지 순서 `optionOrders`, 직전 검토 `lastCheck`를 보존한다. **닫힌 구형 메뉴가 다시 열리는 것**을 기록을 잃는 것으로 취급하지 않지만, 유효한 배치가 사라져서는 안 된다.

주의: 일반적인 문장 완성 과제에는 **사용한 단어 교환이 오히려 부자연스러울 수 있다.** 이 제약은 ‘서로 다른 말을 각 한 번씩 배치한다’는 03B의 과제 계약에서 나왔다. 단어 중복 사용이 필요한 작문·연결어 과제에는 강제하지 않는다.

### 13.6 저장·이야기 경계와 재사용 시 일반화 지점

현재 03B는 `academic-tower-turn-03b-ran-village`라는 **전역 스테이지 ID 하나**와 안정적인 **내부 task ID 여섯 개**를 가진다. 도입/결말은 여정의 story 노드이지만, 중간 두 인물 장면은 전역 여정 노드를 추가하지 않고 스테이지의 일시 상태로 관리한다.

| 저장 영역 | 현재 사용 | 다음 구현의 지침 |
|---|---|---|
| 전역 여정 | `completedStages`, `seenStories`, 잠금·결말 story | 기존 완료·본선 milestone을 곁가지 완료와 섞지 않는다 |
| 작업 공통 | `kind:'meaning-links'` / `schemaVersion:1`, `taskIndex`, `phase`, `answers`, `placements` | ID·정답·저장 호환을 검토. 완료한 내부 과제를 무턱대고 새 문제로 되돌리지 않는다 |
| 03B 중간 이야기 | `phase:'scene'`, `sceneId`, `sceneIndex`, `seenScenes` | **03B 전용 전환 로직**이므로 새 스테이지에서 쓰려면 장면의 트리거/다음 task를 데이터로 표현하도록 분리 |
| 03B 종합 입력 | `slot`, `clozeMenuOpen`, `optionOrders`, `lastCheck` 및 빈칸→표현 `placements` | 배치·드롭다운 열림·오답을 재개해 확인; 새 과제의 중복 허용 여부와 판정은 별도 정의 |
| 재플레이 | 이전 영구 진행에 영향 없는 새 스테이지 임시 상태 | 첫 플레이 결과/아이템/단어 발견을 중복 지급하지 않는다 |
| 옛 저장 마이그레이션 | 03B T6의 옛 *읽기 전용* 미완료 상태를 새 복원 과제로 바꾸되 T1~T5 통과 보존 | **이미 영구 완료한 스테이지**와 *진행 중인 과제 변경*을 구별한다 |

새 스테이지가 03B의 중간 이야기 또는 인라인 드롭다운을 두 번째로 사용하게 될 때는 **복사한 전용 함수 둘**을 만들지 않는다. 그때 다음처럼 **필요한 최소 공통화**를 검토한다.

- 장면 정의에 *어느 task 성공 뒤 재생하고 어느 task로 돌아올지*를 명시하는 데이터 계약
- 슬롯 수·중복 가능 여부·선택지 출처·정오답·선택 UI를 받아 동작하는 종합 복원 렌더러
- story와 stage의 포커스·스크롤·되돌리기·저장 복구를 검증하는 공유 테스트

**지금은 위 일반화가 구현됐다고 표시하지 않는다.** `renderVillageMeaning` / `renderVillageCloze`와 `villageResearch` 분기는 실제로 03B 전용이다. 두 번째 사용처가 만들어진 시점에 G2 사양을 먼저 쓰고, 그만큼만 추출한다.

### 13.7 차기 학술탑 설계 체크 양식

이 양식은 위 11장의 전술형 trigger/predicate 양식을 대체하지 않고, **문서·담화 연구 과제에 덧붙이는 체크 항목**이다.

```text
연구 주제 / 플레이어가 실제로 알아야 할 의미 차이:
연구가 시작되는 이유(의뢰가 아니어도 되는가):
사용할 표현(새 표현 / 능동 복습 / 자연스럽게 등장만 하는 표현):
각 표현의 역할(사건/지속/주장/양보/범위/기타):
각 표현이 요구하는 행동(읽기만/표시/고치기/이어 쓰기/복원):
원본 자료 ID·출처·시점·확인되지 않은 부분:
작업면 실제 작성자(소년/연구원/타인/공동):
화면의 작업 지시와 모바일 조작:
옳은 판단의 근거 / 잘못된 판단의 비약:
중간 대화가 필요한 사건이나 관계 변화(없으면 생략):
종합해서 남길 산출물(필요하지 않으면 생략):
최종 복원이 필요한 이유와 빈칸 수(고정 5개 금지):
재사용할 공통 기반 / 03B 전용이라 추출할 부분:
안정 stage·task·story ID / 기존 완료와의 관계:
중간 저장·재개·되돌리기·재플레이:
375×812 · 375×667 · 375×640 · 360×640 모바일 검사:
실기기에서 확인할 텍스트·선택지·스크롤·터치:
```

**다음 확장(예: 미구현 04A)은 이 도감에서 ‘주제에 필요한 패턴’을 고르되, 03B의 지도를 다시 조사하거나 다섯 빈칸으로 끝내는 구성을 복사하지 않는다.** 연구원의 전문성을 일부러 낮춰 소년의 기여를 만들지 않는다. 서로 다른 근거와 관찰 범위를 잘 아는 두 사람으로 그리는 관계 표현만 가져올 수 있다.
