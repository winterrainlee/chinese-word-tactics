# 1.0 사용자 경험 자동 검수 v0.1

작성일: 2026-09-12  
적용 대상: `chinese-word-tactics` v1.0 전 구간  
목적: 신규 사용자 관찰이 어려운 동안, 모바일 브라우저에서의 플레이·학습·스토리 감상 경험을 자동 브라우저 검수와 대표 화면 스크린샷으로 반복 확인한다.

기준 문서:

- `DESIGN-PRINCIPLES-v0.2.md`
- `STORY-JOURNEY-SYSTEM-v0.1.md`
- `DEVELOPMENT-STATUS.md`
- 각 구역의 최신 설계·구현 기록

이 문서는 기능 단위 테스트를 대체하지 않는다. 기존 자동검사가 `판정이 맞는가`를 확인한다면, 여기서는 다음 두 가지를 추가로 본다.

1. **필요한 정보가 필요한 순간에 보이는가.**
2. **한 행동에서 다음 행동으로 자연스럽게 이어지는가.**

신규 사용자 실제 플레이 검수는 여전히 최종 확인 수단이다. 다만 v1.0 전까지는 이 문서의 자동 검수를 공통 회귀 기준으로 둔다.

---

## 1. 한 줄 합격 기준

> **중국어를 이해한 덕분에 해법을 찾고, 내 행동으로 판과 이야기가 바뀌며, 그 흐름이 화면 이동 때문에 끊기지 않는다.**

---

## 2. 우선순위

### P0 — 진행과 신뢰를 깨는 문제

- 핵심 조작이나 정보가 화면 밖에 가려진다.
- 터치 대상이 겹치거나 지나치게 작다.
- 다음 진행 버튼이 없거나 잘못된 곳으로 간다.
- 스테이지 완료 뒤 본편 진행이 끊긴다.
- 새로고침·복귀 뒤 진행 상태와 화면이 서로 맞지 않는다.

P0는 v1.0 출시 차단 조건이다.

### P1 — 핵심 경험을 약하게 만드는 문제

- 목표보다 부가 정보가 더 강하게 보인다.
- 행동 직후 어떤 변화가 생겼는지 알아보기 어렵다.
- 성공·실패 이유가 판과 연결되지 않는다.
- 스테이지 완료창, 후일담, 다음 스테이지 사이에 같은 정보가 반복된다.
- 다음 행동이 이미 정해져 있는데 의미 없는 확인 화면을 거친다.
- 중국어 단어의 의미보다 버튼 위치나 반복 조작만으로 해결하게 된다.

P1도 v1.0에서 가능한 한 닫는다.

### P2 — 풍성함과 완성도를 높이는 문제

- 연출의 다양성
- 장식의 세밀함
- 부가 편의
- 필수 정보를 가리지 않는 범위의 시각 polish

P2는 핵심 흐름이 성립한다면 v1.0 이후로 넘길 수 있다.

## 3. 화면 정보의 역할

전술 화면의 정보는 다음 세 역할로 나눈다.

### 목표 = 의도

플레이어가 이번 판에서 무엇을 이루려는지 알려준다.

- 처음 진입했을 때 분명해야 한다.
- 플레이 중 잊었을 때 다시 확인할 수 있어야 한다.
- 계속 가장 큰 시각적 요소일 필요는 없다.
- 판이나 상태 메시지가 이미 보여주는 내용을 반복하지 않는다.

### 판 = 현재 상태

지금 세계가 어떤 상태인지 직접 보여준다.

- 플레이어 위치
- 오브젝트 위치
- 수량
- 연결·손상·회복 여부
- 이동 가능 상태
- 조사해서 알아낸 정보

가능하면 상태를 별도 문장으로 외우게 하지 않고 판에 남긴다.

### 상태 메시지 = 직전 행동의 의미

방금 한 행동이 무엇을 바꿨는지 해석한다.

예:

- `水量增加了，但還不夠。`
- `已進入關口。`
- `還沒通過遺跡。`

상태 메시지는 목표 설명을 반복하는 곳이 아니다. `행동 → 변화 → 의미`를 연결하는 피드백이다.

새 화면을 검수할 때 세 영역이 같은 말을 반복한다면 하나를 줄인다.

## 4. 자동 검수 시나리오 UX-01~UX-12

### UX-01 — 최초 스테이지 진입

**질문**

- 스테이지 이름, 목표, 판, 상태, 단어, 조작의 위계가 분명한가?
- 가장 먼저 읽어야 할 것이 목표와 판인가?
- 목표 카드가 작은 화면에서 판을 지나치게 밀어내지 않는가?
- 목표와 규칙 문장이 같은 내용을 반복하지 않는가?
- 단어 뜻 진입이 사전 기능으로 보이고 일반 행동과 구분되는가?
- 항상 보이는 설명형 문장이 실제 첫 판단에 필요한 정보만 담는가?

**자동 확인**

- iPhone 13 mini 세로 viewport에서 첫 화면 스크린샷을 저장한다.
- 최초 렌더에서 핵심 조작이 화면 밖에 있는지 확인한다.
- 목표 영역 높이, 판 영역 높이, 하단 조작 영역 높이를 기록한다.
- 사전 아이콘의 터치 영역과 접근 가능한 이름을 확인한다.

**실패 예**

- 판보다 목표 카드가 더 많은 화면을 차지한다.
- 첫 행동 버튼이 스크롤 전에는 보이지 않는다.
- 목표와 규칙이 사실상 같은 문장이다.
- 단어 뜻 아이콘이 행동 버튼이나 정답 선택지처럼 보인다.
- 판과 조작만으로 알 수 있는 내용을 긴 한국어 문장이 다시 설명한다.

---

### UX-02 — 일반 행동 직후

**질문**

- 변화한 판과 상태 메시지를 한 흐름으로 읽을 수 있는가?
- 상태 메시지가 바뀌었다는 사실을 알아차릴 수 있는가?
- 판 자체에서 바뀐 상태도 확인할 수 있는가?
- 행동 결과와 관련 중국어를 변화한 대상 가까이에서 확인할 수 있는가?
- 행동 전후에 판의 위치와 크기가 유지되는가?

**자동 확인**

- 대표 행동 전/후 스크린샷을 저장한다.
- 상태 메시지 DOM이 실제로 바뀌는지 확인한다.
- 메시지가 viewport 안에 남는지 확인한다.
- 변화한 판 요소와 상태 메시지가 동시에 화면 안에 존재하는지 확인한다.
- 대표 행동 전후 판의 bounding box를 비교한다.

**실패 예**

- 행동 결과는 텍스트에만 있고 판에는 변화가 없다.
- 판은 변했지만 상태 메시지가 화면 아래로 밀려난다.
- 매 행동마다 같은 중립 메시지만 보여 중요한 변화가 묻힌다.
- 상세나 피드백이 나타날 때 판 전체가 이동한다.
- 변화는 숫자·아이콘으로만 끝나고 관련 중국어를 다시 만나지 않는다.

---

### UX-03 — 잘못된 행동

**질문**

- 왜 행동이 성립하지 않았는지 이해할 수 있는가?
- 잘못된 시도가 판 상태를 몰래 바꾸지 않는가?
- 다시 시도할 방법이 남아 있는가?

**자동 확인**

- 금지된 이동, 잘못된 배치, 잘못된 대상 조작을 실행한다.
- 전후 상태를 비교해 불필요한 상태 변경이 없는지 확인한다.
- `info / bad` 피드백이 나타나는지 확인한다.

---

### UX-04 — 핵심 단어 성립

**질문**

- 핵심 단어가 성립하는 순간 판의 변화와 언어 피드백이 연결되는가?
- 단어 버튼의 완료 상태만 바뀌고 실제 세계 변화는 없는 식으로 끝나지 않는가?

**자동 확인**

- 각 런타임의 대표 핵심어 한두 개를 골라 성립 전/후를 캡처한다.
- 판 변화, 상태 메시지, 단어 완료 표시가 서로 모순되지 않는지 확인한다.

---

### UX-05 — 최종 행동과 완료 전환

**질문**

- 마지막 행동의 결과를 사용자가 인지할 시간이 있는가?
- 완료 시트가 세계 변화와 마지막 피드백을 즉시 덮어버리지 않는가?
- 진행 상세가 사용한 단어와 변화의 짧은 복기로 전환되는가?
- 완료 신호가 중복되거나 미충족처럼 보이는 상태와 충돌하지 않는가?

**자동 확인**

- 최종 행동 직후 시점의 스크린샷을 별도로 저장한다.
- 완료 시트가 열리기 전 마지막 판 상태가 실제 렌더되는지 확인한다.
- 최종 상태 메시지와 완료 시트 사이의 전환 시간을 기록한다.

**현재 기준 위험 지점**

기본 전술 런타임은 승리 판정 뒤 약 `120ms` 후 완료 시트를 띄운다. 이 값은 기능상 문제는 없지만, 마지막 판 변화와 성공 메시지가 사실상 읽히지 않을 가능성이 있다. 자동 검수에서 우선 확인한다.

**판정 원칙**

단순한 최소 밀리초 숫자만으로 합격시키지 않는다. 마지막 결과가 시각적으로 확인 가능한 상태가 존재하는지가 핵심이다.

### UX-06 — 스테이지 완료 화면

**질문**

- 다음 본편 진행이 primary action으로 분명한가?
- `다시 해보기`가 본편 진행보다 강하게 보이지 않는가?
- 완료 문장이 직전 상태 메시지를 불필요하게 반복하지 않는가?

**자동 확인**

- 완료 시트 스크린샷을 저장한다.
- primary/secondary 버튼 스타일을 확인한다.
- 첫 플레이와 replay 모드의 버튼 라벨을 각각 검증한다.

### UX-07 — stage → story

**질문**

- 스테이지 완료 뒤 후일담으로 바로 이어지는가?
- 여정 목록이나 월드맵을 불필요하게 경유하지 않는가?
- 완료 시트의 설명과 첫 후일담이 같은 사실만 반복하지 않는가?

**자동 확인**

- 완료 버튼 클릭 뒤 다음 노드 타입과 실제 view를 검사한다.
- 예상 `story` 노드라면 한 번의 진행 행동으로 story view에 도달하는지 확인한다.
- 인접한 `stage.story`와 첫 story beat의 문장을 중복 후보로 기록한다.

문장 중복 검사는 자동 실패보다 **검토 경고**로 취급한다. 의미상 필요한 반복일 수 있기 때문이다.

### UX-08 — story → stage

**질문**

- 사용자가 다시 목록에서 스테이지를 찾아야 하지 않는가?

**자동 확인**

- 마지막 beat에서 버튼 라벨을 읽는다.
- 클릭 뒤 실제 node와 view가 예고와 맞는지 검사한다.

### UX-09 — stage → stage

**질문**

- 이야기 노드가 없는 연속 스테이지는 불필요한 화면을 거치지 않는가?
- 다음 판으로 이동할 때 의미 없는 `확인 → 계속 → 다음` 같은 중복 단계가 없는가?

**자동 확인**

- stage 완료 뒤 다음 actionable tactical state까지 필요한 입력 수를 기록한다.
- 중간에 방문한 view와 sheet 수를 기록한다.

**판정 원칙**

클릭 수 자체는 실패 기준이 아니다. 각 단계가 새 정보나 선택을 제공하는지 함께 기록한다.

### UX-12 — iPhone 13 mini 세로 화면

**질문**

- 모든 대표 상태에서 핵심 정보와 조작이 잘리지 않는가?
- 44px 최소 터치 영역이 유지되는가?
- 6열 판에서도 조작이 가능한가?
- Safari의 작은 viewport에서도 화면 구조가 무너지지 않는가?
- 대상 선택·조사·완료 상태가 바뀌어도 판의 위치와 크기가 안정적인가?

**자동 확인**

대표 viewport를 최소 다음 네 상태로 둔다.

1. `375×812` — iPhone 13 mini 전체 세로 화면에 가까운 비교 기준
2. `375×667` — Safari UI가 펼쳐진 중간 높이 대리값과 `651~700px` compact 규칙 검증
3. `375×640` — 전술 스테이지의 최소 설계·검수 viewport
4. `360×640` — 좁은 폭과 짧은 높이가 동시에 적용되는 회귀 검증

각 viewport에서 진입, 가장 긴 선택, 행동 불가, 행동 직후, 완료 상태를 검사한다.

- `375×640`에서 무스크롤 핵심 UI가 `620px`과 safe-area·바깥 패딩을 뺀 실가용 높이 중 더 작은 예산 안에 있는지 기록한다.
- 상세 시트를 닫은 기본 상태에서는 문서 세로 overflow가 없어야 한다.
- 헤더, 사전 진입, 핵심 행동, 되돌리기의 실제 터치 영역은 `44×44px` 이상이어야 한다.
- 같은 viewport의 상태 전환 전후로 판의 `x / y / width / height`를 비교한다.
- 사용자가 명시적으로 연 사전·상세 시트의 내부 스크롤은 허용하되, 닫은 뒤 판 위치가 복원되어야 한다.

스크린샷과 DOM 크기 검사를 함께 사용한다. 자동 브라우저 수치는 Safari 실기기 통과를 대신하지 않는다.
실기기에서는 주소창·하단 도구막대 상태별 `window.innerHeight`, `visualViewport.height`, 적용된 safe-area 패딩을 따로 기록한다.

### 2026-09-21 전술 레이아웃 실행 결과

네 viewport의 전술 화면 행렬을 자동화했다.

| 검사 | 범위 | 관측 상태 | 결과 |
|---|---|---:|---|
| `smoke_gate_layout.py` | 길목 G1~G7과 튜토리얼 계열 | 80 | PASS |
| `smoke_workshop_layout.py` | 장인골 W1~W7 | 224 | PASS |
| `smoke_market_layout.py` | 장터 M1~M8 | 96 | PASS |
| `smoke_north_forest_layout.py` | 북쪽 숲 F1~F8 | 64 | PASS |

묶음별 행렬은 총 464개 상태 관측이다. 별도의 `smoke_ux.py` 대표 행렬 36개도 통과했다.
각 검사에서 기본 문서 overflow, 44px 최소 조작 영역, 상태 전환 전후 판 bounding box를 확인한다.
장터 검사는 완료 상태를 직접 주입하지 않고 화면의 이동·선택·가져오기·교환·놓기·구매 조작으로 도달한다.

장터 M3의 짧은 화면 판단 트레이는 추가로 다음을 검사한다.

- `max-height:700px`에서 일반 5열 칸이 `46px`이고 44px 터치 하한을 지키는가
- 단순 대상 선택 상태에서 중복 상태 줄이 접히고 판단 트레이가 `140px` 이상 확보되는가
- 소지량, 대상, 필요 수량, 행동 불가 이유가 가로 스크롤 밖에 고정되는가
- 보충 카드 두 장이 가로 overflow 없이 레일 안에 동시에 완전히 보이고 판단 트레이에는 세로 overflow가 없는가
- 공유 `되돌리기`가 M3에서는 `100×44px`로 판단 트레이 안에 들어오고 M4 진입 전에 원래 조작 영역으로 복귀하는가
- 원거리 문맥 행동은 같은 자리를 유지한 채 비활성이고, `放 / 拿`는 104px, `交換`은 136px 안에서 말줄임 없이 보이는가
- 보충 카드는 6px 간격을 제외한 레일 폭을 절반씩 쓰는 약한 정보 면으로 보여 문맥 행동 버튼과 구별되는가
- 완료 시 별도 행을 추가하지 않고 같은 행동 줄을 완료 진행으로 교체해 판 bounding box를 유지하는가
- 행동 결과가 나타나면 보충 레일이 접히고 결과와 핵심 상태가 같은 고정 예산 안에 남는가

이 결과는 자동 Chromium 기준이다. iPhone 13 mini Safari의 주소창·하단 도구막대 상태별 실기기 승인은 별도로 남아 있다.

## 5. 대표 화면 묶음

모든 스테이지의 모든 상태를 이미지 회귀로 고정하지 않는다. 런타임과 정보 구조가 다른 대표 화면을 잡는다.

### 기본 격자

- 튜토리얼 또는 길목 기본 이동판
- 행동 전
- 일반 이동 후
- 실패 피드백
- 최종 행동 직후
- 완료 시트

### 길목 특수 기믹

- 장애물 조사·제거가 있는 G4
- 수레 이동이 있는 G5 또는 G6
- 종합판 G7

### 장인골

- W1 상태 변경/유지
- W3 연결 관계
- W6 손상·수리·회복
- W7 종합판

### 장터

- M1 기본 자원 이동
- M5 선택
- M6 보류
- M7 또는 M8 6열 판
- 상태 패널과 판 위 수량 표시가 함께 보이는 상태

### 이야기·상위 흐름

- 첫 story 화면
- 한국어 뜻을 연 상태
- story 마지막 beat
- stage 완료 시트
- 구역 완료 후 월드맵
- 중단 후 복귀 화면

## 6. 전환 마찰 기록

각 sequence에 대해 다음 값을 기록한다.

```text
from node
→ 중간 sheet/view
→ to node
→ 다음 실제 조작 가능 상태
```

함께 기록할 항목:

- 필요한 사용자 입력 수
- 지나간 view 수
- 지나간 sheet 수
- 새 정보가 있는 단계 수
- 같은 사실을 반복하는 단계 수
- 버튼 라벨과 실제 목적지 일치 여부

### 경고 규칙

다음은 자동 실패가 아니라 검토 경고로 먼저 남긴다.

- `stage.story`와 바로 다음 story 첫 대사가 매우 비슷하다.
- 새 정보가 없는 확인 화면이 연속 두 번 이상 등장한다.
- 다음 actionable state까지 입력 수가 눈에 띄게 늘어난다.
- 월드맵·여정이 sequence 중간에 등장하지만 실제 선택은 없다.

## 7. 자동검사와 사람 판단의 경계

### 자동으로 확정하기 좋은 것

- view가 잘못 열림
- 버튼 라벨과 실제 목적지 불일치
- viewport 밖으로 핵심 조작이 벗어남
- 최소 터치 크기 미달
- 잘못된 행동 뒤 상태 변경
- reload 뒤 node/상태 불일치
- 불필요한 월드맵/여정 경유 여부

### 자동으로 경고만 남길 것

- 목표 카드가 너무 커 보임
- 상태 메시지가 눈에 잘 안 들어옴
- 완료 시트가 너무 빨리 뜸
- 완료 문장과 후일담이 중복됨
- 이야기 전환이 답답하게 느껴짐

이 항목들은 스크린샷과 측정값을 함께 남기고 사람이 최종 판정한다.

## 9. v1.0 적용 순서

1. UX 자동검사 스크립트와 대표 스크린샷 생성 경로를 만든다.
2. 기본 격자·길목·장인골·장터·story·완료 시트의 대표 상태를 먼저 연결한다.
3. `UX-01~12` 결과표를 자동 생성한다.
4. P0 실패를 우선 수정한다.
5. P1 중 `목표/판/상태 메시지 위계`와 `스테이지 간 전환 마찰`을 먼저 검토한다.
6. 여관·1장 결말·첫 자유 의뢰가 붙으면 전체 sequence에 같은 검사를 확장한다.
7. 최종적으로 빈 저장에서 1장 결말과 첫 의뢰까지 자동 완주 흐름을 돌린다.
8. 자동 검수가 안정되면 실제 신규 사용자 테스트에서 이 문서가 놓친 문제를 별도로 추가한다.

## 10. 현재 가장 먼저 확인할 가설

### 가설 A — 목표보다 상태 변화 피드백이 약하다

현재 기본 전술 화면은 목표를 독립 카드로 크게 유지하고, 상태 메시지는 판 아래의 비교적 조용한 영역에 둔다. 플레이 전에는 적절하지만, 행동 이후에는 `방금 무슨 일이 일어났는가`가 더 중요해질 수 있다.

검수에서는 목표 카드의 존재 자체보다 다음을 본다.

- 플레이 중 목표가 과도한 높이를 계속 차지하는가?
- 판과 상태 메시지를 한 시야에서 읽을 수 있는가?
- 중요한 `good / bad / info` 변화가 일반 이동 메시지와 충분히 구분되는가?

### 가설 B — 마지막 세계 변화가 완료 UI에 너무 빨리 묻힌다

기본 전술 런타임의 완료 시트 지연은 현재 약 `120ms`다. 마지막 행동의 결과를 판에서 충분히 볼 수 있는지 대표 스테이지에서 확인한다.

### 가설 C — sequence 구조는 좋지만 완료 문구와 후일담이 중복될 수 있다

현재 story/stage 노드는 월드맵이나 여정을 매번 경유하지 않고 직접 연결된다. 이 구조는 유지하는 것을 기본값으로 한다.

대신 다음 중복을 찾는다.

```text
최종 상태 메시지
→ stage.story가 들어간 완료 시트
→ story 후일담 첫 대사
```

세 단계가 모두 같은 사실을 말한다면 역할을 나눈다.

- 상태 메시지: 방금 생긴 변화
- 완료 시트: 판을 끝냈다는 확인과 다음 행동
- 후일담: 인물·관계·세계의 반응

## 11. 최종 승인 질문

자동 검수와 스크린샷 검토 뒤 다음 질문에 답한다.

1. 첫 화면에서 목표를 이해하면서도 판이 주역으로 보이는가?
2. 행동 직후 어디가 바뀌었고 왜 그런지 바로 연결할 수 있는가?
3. 마지막 행동의 결과를 보고 나서 완료 UI로 넘어가는가?
4. 완료 뒤 다음 이야기나 스테이지를 찾으러 메뉴를 돌아다닐 필요가 없는가?
5. 연속된 화면이 같은 성공 사실을 반복하기보다 각자 다른 역할을 하는가?
6. 작은 모바일 화면에서도 `목표 → 판단 → 행동 → 결과 → 다음 사건`의 흐름이 끊기지 않는가?

이 여섯 질문에 모두 `그렇다`고 답할 수 있어야 v1.0 사용자 경험 검수를 통과한 것으로 본다.
