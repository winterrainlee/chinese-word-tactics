# 지역·스테이지 개발 표준 v0.1

> 상태: 운영 기준
> 적용 대상: 신규 지역, 기존 지역의 신규 스테이지, 자유 의뢰, 지역 후일담
> 목표: 기획부터 GitHub Pages 배포와 iPhone 13 mini Safari 승인까지 같은 완료 기준으로 닫는다.

이 문서는 콘텐츠의 구체적인 이야기를 결정하지 않는다. 제품 원칙은 `AGENTS.md`와 `DESIGN-PRINCIPLES-v0.2.md`, 세계 구조는 최신 `WORLD-*` 문서, 지역별 내용은 해당 지역의 최신 설계 문서를 따른다. 이 문서는 그 내용을 구현하고 검증하는 **개발 절차와 완료 증거**의 기준이다.

지역별 최신 설계와 실제 구현이 달라졌다면 구현 기록에 차이와 이유를 남긴다. 구현 기록은 코드의 현재 동작을 설명할 수 있지만 제품 원칙을 묵시적으로 바꾸지는 않는다.

---

## 1. 두 가지 개발 경로

### A. 기존 지역 확장

기존 월드 장소와 진입 흐름을 유지하면서 스테이지나 의뢰를 추가한다.

필수 범위:

- 목표어와 스테이지 데이터
- `story → stage → story` 여정 연결
- 필요한 범위의 런타임·스타일·자산
- 단어장·어휘 생애주기 편집층
- 지역 단위 테스트와 기존 회귀

### B. 신규 지역 추가

기존 지역 확장의 모든 항목에 다음을 추가한다.

- 안정적인 지역 ID와 월드 메타데이터
- 지도 좌표·아이콘·장소 설명
- 실제 잠금 조건과 추천 조건의 분리
- 여정 section과 `entryRegionId`
- 지역 완료 milestone과 다시 연습하기
- 기존 지역에서 진입하고 다시 돌아오는 종단 흐름

장소가 새로 보인다는 이유만으로 신규 지역을 만들지 않는다. 별도의 공간 기억, 진입점, 의뢰 묶음, 진행 상태를 가져야 할 때 신규 지역으로 분리한다.

## 2. 상태 표기

| 상태 | 의미 | 필요한 증거 |
|---|---|---|
| `⬜` | 범위 미확정 | 없음 |
| `🟨` | 구현 가능한 사양 확정 | 설계 문서, acceptance 항목, 저장 결정 |
| `🧪` | 구현·자동검사 완료 | diff, 로컬 검증 로그, 브라우저 캡처 |
| `✅` | 배포·실기기 승인 완료 | Pages 빌드, iPhone 검수 기록 |

자동 Chromium 결과를 iPhone Safari 승인으로 기록하지 않는다. `🧪 → ✅` 전환에는 실제 기기, 확인 날짜, 배포 빌드, 플레이 경로가 필요하다.

## 3. 표준 개발 게이트

### G0 — 범위와 안정 ID

구현 전에 다음을 결정한다.

- 기존 지역 확장인지 신규 지역인지
- region, stage, story, quest, milestone의 안정 ID
- 실제 잠금 조건과 권장 선행 경로
- 본편인지 자유 의뢰인지
- 첫 플레이와 재플레이의 반환 위치
- 영구 저장할 결과와 스테이지 안에서만 유지할 임시 상태

ID는 저장과 여정에서 사용한 뒤 이름을 바꾸지 않는다. 표시 이름이 바뀌어도 내부 ID는 유지한다.

현재 전술 저장에는 `stageIndex`가 남아 있다. 신규 스테이지는 기존 `STAGES` 중간에 삽입하지 않고 뒤에 추가한다. 사용자에게 보이는 진행 순서는 `JourneyContent`의 sequence로 정한다. 중간 삽입이 필요하면 먼저 ID 기반 저장 migration을 별도 작업으로 완료한다.

통과 조건:

- ID와 저장 경계가 표에 적혀 있다.
- 잠금과 추천이 같은 조건으로 오용되지 않는다.
- 기존 저장을 열었을 때 의미가 바뀌는 ID 또는 배열 순서 변경이 없다.

### G1 — 상황·어휘·기믹 설계

먼저 플레이 상황과 판단을 한 문장으로 쓴다.

```text
플레이어는 [상황]에서 [정보]를 읽고 [판단/행동]하여 [상태 변화]를 만든다.
```

그 다음 어휘를 정한다.

1. 현재 상황에서 기존 단어를 자연스럽게 능동 재사용할 수 있는지 본다.
2. 한 번만 목표어로 등장한 단어 가운데 잘 맞는 것이 있는지 본다.
3. 같은 문제를 복제하지 않고 다른 문맥에서 뜻을 사용하게 한다.
4. 새 개념이 정말 필요할 때만 신규 목표어를 추가한다.
5. 신규 목표어는 판당 1~3개를 기본으로 한다. 의미상 한 묶음인 예외는 근거를 남긴다.

각 목표어는 버튼 효과가 아니라 판 위 관계, 조건, 상태 변화, 자원 이동 중 하나 이상으로 표현한다.

기믹은 다음 순서로 판단한다.

1. 데이터 변경만으로 재사용 가능한가?
2. 기존 공통 판정을 조합할 수 있는가?
3. 두 번째 실제 사용처가 생긴 전용 구현을 필요한 범위까지만 일반화할 것인가?
4. 새 전용 기믹이 꼭 필요한가?

통과 조건:

- 목표어마다 플레이어가 직접 만드는 상태가 있다.
- 오답은 다음 판단에 쓸 정보를 남기며 자연스럽게 복구할 수 있다.
- 새 공통 기믹은 실제 사용처를 근거로 한다.
- 가능한 경우 복수 해법과 행동 순서를 허용한다.

### G2 — 구현 수준 사양

아래 템플릿을 지역 설계 문서의 각 스테이지에 작성한다.

```text
스테이지 ID:
표시 제목: 한국어 / 번체 중국어
지역·의뢰 위치:

상황 한 문장:
학습 단어:
기존 단어 능동 재사용:
문맥어·복습어:

맵:
초기 상태:
플레이어가 볼 수 있는 정보:
직접 탭 정보:
상황형 행동:

재사용할 기믹:
새로 필요한 기믹:

행동/사건(trigger):
조건(predicate):
상태 변화(state delta):
피드백(feedback):
완료 조건(win):

대표 정상 해법:
허용할 다른 해법:
대표 오답:
오답에서 얻는 정보:
복구·되돌리기:

첫 플레이 영구 저장:
재플레이에서 바꾸지 않을 값:
임시 저장 revision 필요 여부:
완료 뒤 다음 story/stage:

```

모바일 사양에는 진입 상태뿐 아니라 정보가 가장 긴 선택 상태, 행동 불가 상태, 행동 직후, 완료 상태를 포함한다.

통과 조건:

- 구현자가 추가 제품 결정을 하지 않고 첫 수직 slice를 만들 수 있다.
- 대표 정상 해법, 오답, 복구, 저장, 재플레이 테스트가 구현 전에 적혀 있다.
- 375×640의 620px 세로 예산과 44×44px 터치 영역을 지킬 정보 위계가 정해져 있다.

### G3 — 작은 수직 slice 구현

한 지역 전체를 한 번에 구현하지 않는다. 서로 같은 공통 판정을 검증하는 1~2개 스테이지 또는 하나의 완결된 의뢰를 기본 slice로 한다.

한 slice는 다음을 함께 끝낸다.

- 도입 story
- 실제 stage
- 완료 판정과 피드백
- 결과 story 또는 명시적인 반환
- 첫 플레이 저장과 재플레이 분리
- 단어 카드와 단어장 연결
- 지역 focused Node 테스트
- 대표 브라우저 완주

파일 책임은 다음 표를 기본으로 한다. 실제로 필요하지 않은 파일은 만들지 않는다.

| 책임 | 기본 위치 |
|---|---|
| 목표어·스테이지 데이터 | `src/<region>-content.js` |
| 이야기·여정 sequence | `src/<region>-journey-content.js` 또는 지역 content |
| 순수 판정·상태 전이 | `src/<region>-runtime.js` |
| 지역 전술 표현 | `src/<region>-runtime.css` |
| 월드 장소 진입 | `src/<region>-world-runtime.js` |
| 단어 관계·지역 색인 | `src/lexicon-content.js` |
| 편집 메타데이터 | `data/vocabulary-lifecycle-v0.1.json`, TBCL 대조 데이터 |
| 계약·기믹 테스트 | `tests/<region>.test.cjs` |
| 실제 브라우저 흐름 | `tests/smoke_<region>.py` |
| 4 viewport 행렬 | `tests/smoke_<region>_layout.py` |

새 스크립트와 스타일은 `index.html`에 상대 경로로 등록하고 의존성 순서를 테스트한다. 신규 smoke 파일은 CI가 자동 발견하지 않으므로 `.github/workflows/deploy.yml`에도 명시적으로 등록한다.

새 classic-script 콘텐츠 파일은 이름을 `*-content.js`로 끝내고 `index.html`에 브라우저 의존성 순서대로 등록한다. 콘텐츠 계약 감사는 이 순서를 그대로 읽고, `src/`에만 존재하고 `index.html`에 빠진 콘텐츠 파일을 오류로 보고한다. 목표어가 들어 있는 파일은 `data/vocabulary-lifecycle-v0.1.json`의 `stageSources`에도 추가한다.

통과 조건:

- 도입부터 결과까지 slice가 끊기지 않는다.
- 데이터만으로 가능한 부분과 전용 런타임의 경계가 설명된다.
- 기존 스테이지 ID와 배열 순서가 보존된다.

### G4 — 자동검증

빠른 전체 콘텐츠 게이트:

```bash
node tools/verify-content.cjs
```

이 명령은 다음을 실행한다.

- 모든 `src/*.js` 문법 검사
- 전체 `tests/*.test.cjs`
- 콘텐츠 교차 참조 감사
- 어휘 생애주기·TBCL 일치 감사
- UX 휴리스틱 감사
- 상태 언어 감사
- 이야기 연결 감사
- 이야기 주음부호 감사

Playwright가 준비된 환경에서 전체 브라우저 게이트까지 실행하려면 다음을 사용한다.

```bash
node tools/verify-content.cjs --browser
```

지역 slice를 구현하는 동안에는 관련 Node 테스트와 smoke를 먼저 반복하고, `🧪`로 바꾸기 전에 전체 게이트를 실행한다.

통과 조건:

- 모든 자동검사가 종료 코드 0이다.
- journey의 모든 stage/story/requires 참조가 실제 콘텐츠와 연결된다.
- `words[]`, 단어장, lifecycle, TBCL 편집층 사이에 누락이 없다.
- 대표 정상 해법, 오답, 복구, 되돌리기가 통과한다.
- 첫 플레이 outcome/milestone과 재플레이가 섞이지 않는다.
- 375×812, 375×667, 375×640, 360×640에서 overflow와 44px 위반이 없다.
- `/chinese-word-tactics/` 하위 경로에서 정적 자원이 로드된다.

### G5 — Pages 배포

작게 완결된 slice를 `main`에 반영한다. CI가 전체 검증을 통과한 뒤 Pages를 배포한다.

확인 항목:

- CI의 모든 필수 job 통과
- 라이브 페이지의 `cwt-build`가 최신 빌드인지 확인
- 변경된 JS/CSS의 cache key 갱신
- 상대 경로 자산의 404 없음
- 빈 저장, 기존 저장, 진행 중 저장에서 진입 가능

Pages 통과만으로 `✅`로 바꾸지 않는다.

### G6 — iPhone 승인과 마감

iPhone 13 mini Safari 세로 화면에서 다음을 확인한다.

- 주소창·하단 도구막대가 펼쳐진 상태와 접힌 상태
- 빈 저장에서 첫 진입과 완주
- 새로고침과 이어하기
- 완료 후 다시 플레이
- 단어 카드 열기와 닫기
- 이동, 기다리기, 직접 정보 확인, 상황형 행동, 되돌리기
- 가장 긴 선택 상태에서 판과 핵심 행동이 잘리지 않는지
- 기존 지역에서 신규 콘텐츠로 들어가고 다시 돌아오는 흐름
- 신규 콘텐츠 완료가 기존 본편 진행과 저장을 오염시키지 않는지

검수 기록:

```text
확인 날짜:
기기·OS:
Safari 상태: 주소창/도구막대 펼침·접힘
Pages 빌드(cwt-build):
시작 저장: 빈 저장 / 기존 저장 / 진행 중 저장
플레이 경로:
첫 플레이 결과:
재플레이 결과:
새로고침·이어하기 결과:
레이아웃·터치 결과:
발견한 문제와 즉시 수정:
최종 상태: 🧪 / ✅
```

마감할 때 다음도 함께 갱신한다.

- `data/vocabulary-lifecycle-v0.1.json`
- 지역 구현 기록
- `docs/DEVELOPMENT-STATUS.md`
- 새로 검증된 공통 규칙이 있으면 `docs/REUSABLE-MECHANICS-v0.1.md`
- 문서 색인 `docs/README.md`

## 4. Definition of Ready

다음 항목을 모두 만족해야 제품 코드 구현을 시작한다.

- [ ] 기존 지역 확장/신규 지역 경로가 정해졌다.
- [ ] 모든 안정 ID와 표시 이름이 구분되어 있다.
- [ ] 상황과 플레이어 판단이 한 문장으로 설명된다.
- [ ] 기존 목표어의 능동 재사용 후보를 검토했다.
- [ ] 신규 목표어와 예외 근거가 정해졌다.
- [ ] 각 목표어가 판 위 관계·상태 변화로 표현된다.
- [ ] 대표 정상 해법, 오답, 복구가 정해졌다.
- [ ] 첫 플레이, 재플레이, milestone, outcome 경계가 정해졌다.
- [ ] 자동 acceptance와 iPhone 관찰 질문이 적혀 있다.
- [ ] 이번 slice에서 만들지 않을 것이 적혀 있다.

---

## 5. Definition of Done

- [ ] 작은 수직 slice의 story → stage → story/return이 완주된다.
- [ ] 신규 스테이지가 기존 `STAGES` 뒤에 추가됐다.
- [ ] 단어장·lifecycle·TBCL 편집 데이터가 실제 `words[]`와 일치한다.
- [ ] 첫 플레이 저장과 재플레이가 본편 진행을 섞지 않는다.
- [ ] `node tools/verify-content.cjs`가 통과한다.
- [ ] 지역 smoke와 4 viewport 행렬이 통과한다.
- [ ] GitHub Pages 하위 경로에서 자산이 로드된다.
- [ ] iPhone 13 mini Safari 실기기 검수를 통과했다.
- [ ] 구현 기록과 개발 상황판에 날짜·빌드·경로가 남았다.
- [ ] 상태가 `✅`로 갱신됐다.

## 6. 당장 하지 않는 구조 변경

이 표준을 도입하기 위해 기존 콘텐츠를 전부 JSON이나 새 프레임워크로 옮기지 않는다. 현재 classic script의 로드 순서와 지역별 런타임을 유지하고, 교차 참조 감사로 누락을 먼저 막는다.

다음 신규 지역을 실제로 추가할 때 등록 지점이 다시 중복되면 그때 region/stage manifest 또는 생성 파이프라인을 별도 설계한다. 표준화의 첫 목표는 추상화가 아니라 **같은 완료 기준과 누락 없는 검증**이다.
