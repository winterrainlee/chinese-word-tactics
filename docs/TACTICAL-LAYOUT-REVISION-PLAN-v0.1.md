# 전술 스테이지 기본 레이아웃·개별 조정 실행 계획 v0.1

> 작성일: 2026-09-20 / 실행 결과 갱신: 2026-09-22
> 상태: 자동 구현·검증 완료, iPhone 13 mini Safari 실기기 검수와 장터 후속 개선 반영
> 기준 문서: `DESIGN-PRINCIPLES-v0.2.md`, `UX-AUTOMATED-REVIEW-v0.1.md`
> 대상: 튜토리얼, 길목 G1~G7, 장인골 W1~W7, 장터 M1~M8, 북쪽 숲 자유 의뢰 F1~F8의 전술 진행 화면
> 목표: iPhone 13 mini Safari의 짧은 실가용 높이에서도 판, 판단 정보, 핵심 행동, 되돌리기를 한 화면에 유지한다.

---

## 1. 결정 사항

앞으로 전술 스테이지는 다음 계약을 먼저 만족해야 한다.

- 최소 설계·검수 viewport: `375×640 CSS px`
- 무스크롤 핵심 UI의 최대 높이: `620px`
- 좁은 폭 보조 검수: `360×640`
- 중간 높이 compact 검수: `375×667`
- 넉넉한 높이 비교 기준: `375×812`
- 최소 터치 영역: `44×44px`

한 화면 유지 여부는 진입 상태가 아니라 정보가 가장 긴 선택·행동 상태로 판정한다.
사전이나 사용자가 명시적으로 연 상세 시트만 내부 스크롤을 허용한다.
기본 플레이에서 페이지 전체 스크롤을 핵심 행동 경로로 사용하지 않는다.

실제 핵심 UI 예산은 `620px`과 `visualViewport.height`에서 계산된 상·하단 safe-area 및 바깥 패딩을 뺀 값 중 더 작은 쪽이다.
브라우저 UI로 이미 줄어든 `visualViewport.height`에서 도구막대 높이를 다시 빼지 않는다.

`375×812`에서 남는 높이는 판의 안정적인 위치와 여백에 사용한다.
큰 화면에서만 추가 설명을 상시 노출하지 않는다.

---

## 2. 감사 기준선

2026-09-20 자동 렌더와 Astra medium 검토에서 다음 상태를 확인했다.

| 대표 상태 | 375×667 결과 | 해석 |
|---|---:|---|
| G1 진입 | 31px 초과 | 공통 간격과 판 크기의 소폭 조정으로 해결 가능 |
| W2 진입 | 33px 초과 | 반복 설명과 장식 높이를 먼저 줄이면 해결 가능 |
| M8 진입 | 초과 없음 | 진입만 보면 맞지만 선택 상태까지 같은 판 위치를 예약해야 함 |
| M8 가장 긴 선택 | 188px 초과 | 여백 축소만으로 해결할 수 없고 상세 구조를 접어야 함 |

추가로 `360×640`에서는 기존 `max-height:650px` 규칙이 작동해 기하학적으로 들어오지만, `.wordbtn`이 42px로 줄어 44px 터치 기준을 위반한다.
반대로 `375×667`은 해당 규칙이 적용되지 않아 640px보다 더 큰 화면에서 넘침이 발생한다.

따라서 이번 작업은 단순히 breakpoint 숫자를 높이는 일이 아니다.
터치 영역을 보존하는 새 `651~700px` compact 규칙과, 긴 상세를 기본 화면에서 분리하는 정보 구조 변경이 함께 필요하다.

## 3. 목표 기본 레이아웃

전술 진행 화면의 기본 순서는 다음과 같다.

`헤더 → 짧은 목표·사전 → 고정된 판 → 상황·수량 요약 → 핵심 행동·되돌리기`

필요한 경우 핵심어는 목표나 상황 가까이에 합쳐 독립 단어 줄 하나를 회수할 수 있다.
중국어 단어 자체는 유지하고 사전 아이콘이 이를 대신하지 않게 한다.

### 항상 보이는 영역

- 현재 스테이지와 재시작·메뉴 진입
- 짧은 중국어 목표와 사전 진입
- 현재 위치, 선택, 행동 가능, 직전 변화가 구별되는 판
- 다음 행동에 필요한 대상, 수량, 가격·교환 조건, 운반 한도, 행동 불가 이유
- 현재 가능한 핵심 행동과 되돌리기

### 필요할 때 여는 영역

- 한국어 상시 번역
- 품목별 장문 설명
- 이미 보이는 판 상태를 다시 풀어쓴 문장
- 여러 부가 행동과 세부 규칙
- 긴 완료 해설

### 상태가 바뀌어도 고정할 것

- 판의 `x / y / width / height`
- 상황 요약이 차지하는 기본 높이
- 핵심 행동과 되돌리기의 위치
- 사전 진입의 위치와 44px 터치 영역

## 4. 구현 단계

### 단계 0 — 측정 기준과 회귀 장치 고정

제품 코드를 바꾸기 전에 현재 대표 상태를 다시 캡처하고 숫자를 저장한다.

1. `375×812`, `375×667`, `375×640`, `360×640` viewport를 테스트 행렬에 추가한다.
2. 진입, 가장 긴 선택, 행동 불가, 행동 직후, 완료 상태를 캡처한다.
3. 문서 높이, 마지막 조작 하단, 판 bounding box, 터치 영역을 기록한다.
4. 사전·상세를 닫은 상태와 연 상태를 구분한다.
5. G1, W2, M8을 대표 fixture로 고정한다.

완료 조건:

- 현재 실패가 수치와 스크린샷으로 재현된다.
- 구현 뒤 같은 명령으로 전후를 비교할 수 있다.
- 자동 Chromium 결과를 Safari 실기기 통과로 잘못 기록하지 않는다.

### 단계 1 — 공통 전술 셸 수정

후보 파일은 `src/styles.css`, `src/ux-play.css`, `src/view.css`, `src/ux-play-runtime.js`, `tests/smoke_ux.py`, `tests/ux-contract.test.cjs`다.
실제 책임이 없는 파일은 건드리지 않는다.

1. `651~700px` 높이 구간에 터치 영역을 줄이지 않는 compact 규칙을 추가한다.
2. `max-height:650px`에서 42px이 되는 단어 버튼을 44px 이상으로 복원한다.
3. 간격·패딩·장식 높이를 height token으로 정리하되 새 프레임워크나 범용 레이아웃 엔진은 만들지 않는다.
4. 판을 남는 공간의 중앙에 매번 재배치하지 않고, 같은 스테이지 상태 사이에서 위치가 유지되도록 상황 영역 예산을 예약한다.
5. 사전 진입을 이모지 또는 SVG 아이콘으로 바꾸되 중국어 단어와 44px 터치 영역, 접근 가능한 이름을 유지한다.
6. 긴 상세가 필요한 런타임을 위해 짧은 상황 요약과 명시적 상세 진입 패턴을 만든다.

완료 조건:

- 공통 CSS만 적용한 상태에서도 G1·W2의 초과량이 줄고 모든 터치 영역이 44px 이상이다.
- 기존 이동, 조사, 기다리기, 되돌리기, 단어 시트, 완료, 저장 동작이 유지된다.
- 상태 전환 전후 판 bounding box 차이가 레이아웃 반올림 범위인 1px 이하다.

### 단계 2 — 대표 스테이지 세 개 조정

#### G1 — 공간 이동 기준

- “목표와 지형을 보고 네 길을 찾아봐.”처럼 새 판단 정보를 주지 않는 안내를 기본 화면에서 제거한다.
- 상태·결과 영역의 자리는 유지해 행동 뒤 판이 밀리지 않게 한다.
- 간격만으로 부족할 때 셀을 48~49px까지 줄일 수 있다. 44px 미만으로 줄이지 않는다.
- `進入 / 退出`과 길표지 조사의 의미 연결은 유지한다.

#### W2 — 장치형 기준

- “불과 바람을 함께 본다”는 조건을 한 번만 전달한다.
- 장치 그림과 주변 장식의 높이를 줄이되 `＋ / −`, 불·바람 상태, 관련 중국어를 유지한다.
- 한쪽만 맞춘 중간 상태와 두 상태를 맞춘 완료 상태가 혼동되지 않게 한다.

#### M8 — 긴 대상 상세 기준

- `已查看晚到的貨。`와 바로 아래 대상 제목처럼 같은 선택을 반복하는 영역을 통합한다.
- 기본 화면에는 대상명, 중국어 품목·수량, 소지 요약, 현재 행동 조건, 핵심 행동만 둔다.
- 품목별 한국어 뜻과 상세 규칙은 사전·상세 시트로 옮긴다.
- “가까이 가야 행동할 수 있음”은 판만으로 자명하지 않으므로 행동 자리에서 짧게 유지한다.
- 진입, 원거리 선택, 인접 선택, 가져오기, 완료 상태에서 판 위치를 고정한다.

완료 조건:

- 세 대표 스테이지의 기본 플레이 상태가 `375×640`에서 620px 상한과 safe-area를 반영한 실가용 예산 안에 들어온다.
- M8 상세를 닫은 상태에서는 페이지 스크롤 없이 핵심 행동과 되돌리기가 보인다.
- 상세를 연 상태에서만 상세 영역 내부 스크롤을 허용한다.

### 단계 3 — 스테이지 묶음별 확장

대표 스테이지가 통과한 뒤에만 같은 문법을 다른 스테이지로 확장한다.

| 묶음 | 주요 조정 | 보호할 것 |
|---|---|---|
| 튜토리얼·길목 G1~G7 | 격자 높이, 반복 안내, 조사·이동 상태 영역 | 위험 회피, 거리·범위, 수레·추종 판정과 공간 기억 |
| 장인골 W1~W7 | 장치 그림 높이, 조건·결과 중복, 상태 요약 | 불·바람·연결·손상·회복의 서로 다른 표식 |
| 장터 M1~M8 | 대상·품목 요약, 번역과 세부 행동의 점진적 공개 | 수량, 가격, 교환, 선택, 분배, 운반 한도 |
| 북쪽 숲 F1~F8 | 7열 판과 참고 영역 밀도, 긴 대상명·특징 요약 | 44px 칸, 방향·특징·안전 판단과 의뢰별 규칙 |

각 묶음은 한 번에 전체 CSS를 다시 설계하지 않는다.
대표 패턴을 재사용할 수 있는 실제 두 번째 사용처가 확인될 때만 필요한 범위까지 공통화한다.

### 단계 4 — 통합 회귀와 실기기 승인

1. 모든 스테이지 진입과 대표 최장 상태를 자동 캡처한다.
2. 기존 해법으로 이동, 조사, 기다리기, 되돌리기, 완료를 재실행한다.
3. 첫 플레이와 재플레이가 본편 저장을 섞지 않는지 확인한다.
4. `/chinese-word-tactics/` 하위 경로에서 정적 자원을 확인한다.
5. iPhone 13 mini Safari에서 주소창·하단 도구막대가 펼쳐진 상태와 접힌 상태를 각각 측정한다.
6. 실기기에서 `window.innerHeight`, `visualViewport.height`, 계산된 상·하단 패딩, 마지막 조작 하단을 기록한다.

자동 검사는 구현 gate이고, 최종 승인은 Safari 실기기 확인 뒤에만 내린다.

## 5. 모델별 작업 분배

OpenAI 공식 모델 분류는 Astra를 가장 어려운 종단 간 작업용, Sol을 복잡한 전문 작업용, Terra를 지능과 비용의 균형형, Luna를 비용 민감·고빈도 작업용으로 설명한다.
이 계획은 먼저 높은 정확도로 기준을 만들고, 검증 가능한 작은 작업을 더 작은 모델로 내리는 방식을 따른다.

참고:

- [OpenAI 모델 목록](https://developers.openai.com/api/docs/models)
- [OpenAI 모델 선택 가이드](https://developers.openai.com/api/docs/guides/model-selection)

| 모델 | effort | 맡길 일 | 맡기지 않을 일 | 산출물·완료 증거 |
|---|---|---|---|---|
| **Astra** | medium | 모바일 게임·학습 설계 관점의 정보 위계 감사, G1·W2·M8 대표 렌더 비교, 설명 삭제가 학습 고리를 끊는지 검토 | 반복 CSS 수정, 전 스테이지 기계적 편집 | 상태별 `유지/축소/접기/제거` 표, 높이 위반 목록, 스크린샷 근거 |
| **Terra** | medium | 공통 전술 셸, `651~700px` compact 규칙, 고정 판·상황 영역, 테스트 측정 도구처럼 여러 파일을 잇는 구현 | 이미 패턴이 고정된 단순 반복 편집 | diff, 대표 viewport 측정값, 관련 Node·Playwright 로그 |
| **Luna** | medium | 공통 패턴 확정 뒤 한 스테이지 묶음씩 적용, 스테이지별 설명 정리, fixture와 회귀 테스트 추가 | 공통 구조를 새로 결정하거나 여러 런타임 충돌을 임의 해결 | 지정 파일만의 diff, 묶음별 높이 표, 해법·저장 회귀 로그 |
| **Luna** | low | 문구 중복 제거, 정확한 상수·테스트 행렬 반영, 스크린샷 목록과 문서 표 갱신처럼 범위가 완전히 정해진 작업 | 정보 우선순위 판단, M8 상세 구조 결정 | 작은 diff와 deterministic test 결과 |
| **Sol** | high | 공통 셸과 대표 세 스테이지가 끝난 뒤 통합 코드·접근성·회귀 위험 검토, 런타임 간 충돌 원인이 불명확할 때 진단 | Astra와 같은 시각 의견을 중복 생산하거나 전 스테이지 반복 수정 | 심각도별 코드 리뷰, 재현 명령, 수정 필요 파일과 acceptance gap |

### Astra 사용 시점

1. 현재 감사 결과를 설계 기준선으로 사용한다. 같은 입력으로 구현 전에 다시 호출하지 않는다.
2. 단계 2의 G1·W2·M8 렌더가 나온 뒤 Astra medium으로 한 번 재검토한다.
3. 대표 패턴에 새로운 정보 구조가 추가되지 않았다면 전 스테이지 적용 후에는 자동·실기기 검수로 끝낸다.
4. 새로운 패턴이 생겼거나 대표 검토와 실제 적용이 크게 달라졌을 때만 최종 Astra 감사를 추가한다.

Astra는 이 작업에서 독립적인 제품·학습 UX 검토자다.
직접 구현까지 맡기지 않아 구현자의 자기 검증과 설계 검토를 분리한다.

### Sol 사용 시점

- 단계 2가 끝난 뒤, 대량 확장 전에 Sol high가 공통 diff와 대표 스테이지를 한 번 검토한다.
- 저장·상태 전환·런타임별 CSS가 얽혀 Terra medium으로 원인을 확정하기 어려운 경우에만 진단을 맡긴다.
- Astra를 실행할 수 없을 때는 Sol high가 디자인 감사의 대체 검토자다. 정상 상황에서는 Astra의 제품 판단과 Sol의 코드 통합 판단을 중복시키지 않는다.

### Terra와 Luna의 경계

- **새 패턴을 만드는 일:** Terra medium
- **검증된 패턴을 한정된 스테이지 묶음에 적용하는 일:** Luna medium
- **정확한 지시를 그대로 반영하는 작은 편집:** Luna low
- Luna 결과가 acceptance test를 통과하지 못하면 같은 단계에서 근거 없이 반복하지 않는다. 실패 스크린샷과 로그를 붙여 Terra medium으로 승격한다.
- 여러 런타임의 상태를 동시에 추적해야 하거나 원인이 불명확하면 Terra high로 승격한다.
- 보안·저장 손상·광범위 회귀처럼 오판 비용이 큰 통합 문제만 Sol high에 맡긴다.

## 6. 위임과 병렬 작업 규칙

공통 셸이 확정되기 전에는 개별 스테이지 구현을 병렬로 시작하지 않는다.
공통 CSS와 각 런타임이 동시에 바뀌면 높이 차이의 원인을 분리하기 어렵기 때문이다.

권장 순서는 다음과 같다.

`기준선 측정 → Terra 공통 셸 → Terra 대표 3종 구현 → Astra 제품 검토 + Sol 통합 검토 → 수정 → Luna 묶음별 확장 → 전체 자동검사 → Safari 실기기 승인`

묶음별 확장 단계에서는 다음 범위로 병렬화할 수 있다.

- 작업 A: 튜토리얼·길목 전용 파일과 테스트
- 작업 B: 장인골 전용 파일과 테스트
- 작업 C: 장터 전용 파일과 테스트
- 작업 D: 북쪽 숲 전용 파일과 테스트

각 작업은 공통 CSS를 직접 수정하지 않는다.
공통 변경이 필요하면 제안과 실패 fixture만 반환하고, 메인 작업자가 Terra 범위의 별도 변경으로 처리한다.

모든 서브에이전트 요청에는 다음을 포함한다.

- 수정 허용 파일
- 재현할 viewport와 상태
- 지켜야 할 중국어·규칙·저장 동작
- 실행할 acceptance test
- 전후 수치 또는 스크린샷 경로

완료 판정은 에이전트의 성공 주장 대신 diff, 명령 로그, DOM 측정값, 렌더 이미지로 한다.

## 7. 최종 acceptance gate

### 레이아웃

- `375×640`에서 핵심 UI의 bounding span이 620px 이하이며 safe-area·바깥 패딩을 제외한 실가용 높이도 넘지 않는다.
- 기본 상태에서 문서 세로 overflow가 없다.
- 핵심 행동과 되돌리기가 스크롤 없이 보인다.
- `375×667`에서 640px보다 레이아웃이 더 크게 넘치는 역전이 없다.
- `360×640`에서 가로 overflow가 없고 모든 조작이 44px 이상이다.
- 같은 viewport의 상태 전환 전후 판 위치와 크기 차이가 1px 이하다.

### 정보와 학습

- 중국어 핵심어가 사전 아이콘으로 대체되지 않는다.
- 비언어 단서로 행동한 뒤 관련 중국어 결과를 확인할 수 있다.
- 삭제한 설명 없이도 첫 유효 행동과 현재 상태를 합리적으로 판단할 수 있다.
- 행동 불가 이유와 필요한 수량·조건은 기본 화면에서 확인할 수 있다.
- 완료 상태는 진행 상세를 짧은 의미 복기로 바꾸고 미충족처럼 보이는 정보를 남기지 않는다.

### 기능과 접근성

- 이동, 위험 회피, 기다리기, 조사, 되돌리기, 단어 시트, 완료, 저장이 기존과 같다.
- 사전 아이콘은 접근 가능한 이름과 44px 터치 영역을 가진다.
- 상세 시트는 닫기와 핵심 조작을 잃지 않고 내부 스크롤된다.
- 큰 글자나 더 짧은 실가용 높이에서는 페이지 스크롤 안전망이 내용을 잘라 버리지 않는다.
- 첫 플레이와 재플레이 저장이 섞이지 않는다.

### 실기기 회귀 원칙

자동 Chromium 검증 뒤 iPhone 13 mini Safari에서 주소창·하단 도구막대가 펼쳐진 상태와 접힌 상태를 확인한다.
장터는 이 반복 검수에서 판을 줄이고 판단 트레이를 확보하는 방향, 한 화면에 보충 카드 두 칸을 완전히 노출하는 방향, 짧은 문맥 버튼을 내용 폭에 맞추는 방향으로 보정했다.
다음 값은 이후 전술 화면에도 같은 방식으로 기록한다.

1. `window.innerHeight`
2. `visualViewport.height`
3. 적용된 상·하단 safe-area와 바깥 패딩
4. 마지막 핵심 조작의 하단 좌표
5. 사전·상세를 닫은 기본 상태의 페이지 세로 overflow

실기기 검증에서 초과가 나오면 정보나 터치 영역을 줄이지 않고, 먼저 간격·장식·반복 문장을 조정한다.

### 장터 후속 검수에서 확정한 설계 교훈

1. **판보다 판단을 먼저 줄이지 않는다.** 5×5 장터 판은 44px 터치 영역을 지키는 범위에서 작게 만들고, 회수한 세로폭은 소지품·대상 요약·행동에 배정한다.
2. **현재 가진 자원이 첫 줄이다.** 들고 있는 품목과 구매에 쓸 돈은 같은 1차 크기로 표시한다. 운반 한도만 보조 크기로 낮춘다.
3. **비교 레일은 두 칸을 기준으로 한다.** 첫 화면에 카드 두 장이 완전히 보여야 하며, 세 번째부터만 가로 스크롤한다. 필수 목적지는 선택 대상을 제외한 첫 두 칸 안에 우선 배치한다.
4. **가로 스크롤은 보충 정보에만 쓴다.** 행동, 부족 이유, 현재 소지, 선택 대상은 스크롤 밖에 고정한다.
5. **완료 목적지는 필요량을 선언한다.** 물건을 받는다는 `accepts`와 필요한 수량인 `needs`를 구분하고, 판 배지·요약·비교 카드·완료 판정이 같은 데이터를 사용한다.
6. **같은 사실의 반복과 필요한 사실의 누락을 함께 검사한다.** 선택 대상이 요약과 카드에 중복되지 않는지, 반대로 M7 창고처럼 완료에 필요한 장소가 조사·비교 정보에서 빠지지 않는지 모두 확인한다.

장터 레이아웃 회귀 fixture는 M4의 돈, M5의 두 선택지, M7의 창고 필요량, M8의 상세 시트를 대표 상태로 둔다.
각 상태에서 `375×812`, `375×667`, `375×640`, `360×640`의 문서 overflow, 44px 터치 영역, 판 위치, 첫 두 비교 카드, 자원 갱신을 함께 검사한다.
